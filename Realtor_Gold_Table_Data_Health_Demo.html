The use case

One table that answers: which listing sources can we trust today?

Silver already separates good listings from rejected ones, and records why each one was rejected. The gold table rolls that up so a business user can read it without writing SQL. There is one row per listing source per load date.

Volume

Total listings received, valid count and rejected count

Reject rate

Rejected divided by total, per source

Reasons

Counts by rejection reason: null price, negative price, duplicate ID, orphan property, future timestamp, schema drift

Completeness

Share of valid listings with price, living area, city and agent filled in

Health status

Green under 5% rejects, Amber 5–20%, Red above 20% or any schema drift
Silver (valid)+Rejected (with reasons)→Aggregate by source and load date→Reconcile and assert→Gold: data health

Why it is important

The business reasons. Realtor.com specifics are hypotheses to validate, not facts.

Protect trust in search and AI

Stale, missing or wrong listings are what shoppers see. A health score per source shows where trust is at risk before users notice.

Manage MLS relationships with evidence

Partnerships can see which feeds are healthy and which are slipping, and raise specific issues with each MLS.

Catch breakage early

A renamed field shows up as a reject spike and a Red status within hours, not through complaints.

Free up engineering time

One shared table replaces manual feed checking and ad hoc “is the data OK?” questions.

Gate AI and search features

A rule such as “only use sources that are Green” gives AI experiences a trustworthy supply.

Faster onboarding of new feeds

New sources are held to the same standard, so “is this feed ready?” has a clear answer.
The one-line pitchKnow which listing sources you can trust, and prove it, so engineers fix problems before shoppers see them.

The prompt for Mission Control

Paste this into the Prompt box when you create the task.

Using the silver listings tables in this project (REA_MLS_LISTINGS_SILVER and REA_MLS_LISTINGS_REJECTED), build a gold table called REA_MLS_LISTING_DATA_HEALTH_GOLD for Realtor.com's data and MLS partnerships teams.

Grain: one row per listing source (use the DW_SOURCE column, or the MLS identifier if one exists) per load date.

Include these measures:
- Total listings received (valid plus rejected)
- Valid listing count and rejected listing count
- Reject rate (rejected divided by total received)
- Rejected counts broken out by rejection reason (for example null price, negative price, duplicate listing ID, orphan property, future timestamp, and schema drift)
- Completeness percentage for key fields among valid listings: list price, living area, city, and listing agent
- A simple health status: Green if the reject rate is under 5 percent, Amber if 5 to 20 percent, Red above 20 percent or if any rows are rejected for schema drift

Requirements:
- Reconcile the counts: valid plus rejected must equal total received for each source and load date.
- Follow the project's naming conventions, and include the standard DW audit columns (load date, source, batch ID).
- Add an Assert that the table is not empty and that valid plus rejected equals total received.
- Make the load idempotent, so a rerun on the same load date does not create duplicates.
- Run the pipeline, sample the output, and summarize what you built and what the results show.

Before building, show me your plan, including the tables and columns you intend to use, and wait for my approval.
